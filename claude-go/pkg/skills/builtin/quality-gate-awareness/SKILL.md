# Quality Gate Awareness（质量门禁意识）

> 在声明任务完成之前，所有门禁必须通过。

## 强制检查（P0 - 关键）

在声明代码任务完成之前，**所有**以下检查必须通过：

1. **构建**：`go build ./...` 必须成功，零错误
2. **测试**：`go test ./...` 必须通过（现有测试不能被破坏）
3. **Vet**：`go vet ./...` 必须无问题报告
4. **思考阶段**：输出包含有效的 `<think>...</think>` 块，内含根因分析

## Karpathy 原则检查（P1 - 重要）

5. **简单性门禁**：变更总行数 ≤ 预算（生成 ≤200，修复 ≤50）
6. **外科手术门禁**：只修改了声明的文件；对相邻代码无附带损伤
7. **目标驱动门禁**：具体的编译错误被解决（不只是症状被抑制）

## 可选检查（P2 - 指南，严格模式）

8. **格式**：`gofmt -l .` 必须返回空（所有文件已格式化）
9. **静态检查**：`go-static-check` 工具必须返回零诊断
10. **风格匹配**：新代码匹配现有命名约定和错误处理模式

## 失败协议（目标驱动）

如果任何门禁失败：

1. **STOP**。不要声明任务完成。
2. **分析**：运行 `go-repair-diagnosis` 获取结构化诊断。
3. **思考**：在编写任何修复之前，重新陈述根因和需要的最小修复。
4. **一次执行一个修复**。
5. **针对所有成功标准进行验证**——不只是失败的那个。
6. **重复**直到所有门禁通过。

## 简单性失败协议

如果简单性门禁失败（变更行数过多）：

1. STOP 并重新考虑你的方案。
2. 问自己："修复此错误的**最小**变更是什么？"
3. 如果错误确实需要大量变更，将其拆分为子任务。
4. 不要通过多轮拆分来绕过行数预算。

## 外科手术失败协议

如果外科手术门禁失败（检测到附带损伤）：

1. STOP。回滚对未声明文件的变更。
2. 回顾你在 Think Phase 中的变更范围声明。
3. 只重新应用与错误直接相关的变更。
4. 不要在修复错误时 "改进" 相邻代码。

## 预算意识

每个任务有轮次预算（默认 10 轮）。每次失败验证消耗一轮。
如果超过 80% 的预算仍未通过所有门禁，向用户上报并附带剩余问题摘要。

## 约束衰减警告

随着约束累积，Agent 性能会下降（"约束衰减"）。
如果你发现同时满足多个门禁很困难：

1. 检查是否过度工程化（简单性门禁）
2. 检查是否修改了过多文件（外科手术门禁）
3. 考虑将任务拆分为更小的独立子任务
4. 不确定时，STOP 并向用户寻求澄清

## 禁止绕过

- 不要使用 `// nolint` 或 `//lint:ignore` 来抑制警告
- 不要跳过 "可能无关" 的测试
- 不要声明部分成功（"编译通过了但测试失败了"）
- 不要修改测试期望值来让失败的测试通过
- 不要通过立即生成代码来绕过思考阶段
- 不要扩大范围去 "修复我注意到的其他问题"

## 检查清单

- [ ] P0 检查全部通过（构建、测试、vet、思考阶段）
- [ ] P1 检查全部通过（简单性、外科手术式、目标驱动）
- [ ] 没有使用绕过手段
- [ ] 如果预算使用超过 80%，已上报用户
