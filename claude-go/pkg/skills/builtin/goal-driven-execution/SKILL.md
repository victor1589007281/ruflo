# Goal-Driven Execution（目标驱动执行）

> 关注"成功是什么样"，而非"按什么步骤做"。

## 声明式成功标准

每个任务的成功标准必须是**声明式**的（描述状态），而非**命令式**的（描述步骤）：

| 命令式（错误） | 声明式（正确） |
|-------------|-------------|
| "打开文件，添加函数，保存" | "目标文件包含满足接口 X 的新函数" |
| "运行 go build 检查错误" | "`go build ./...` 返回零错误" |
| "修改测试使其通过" | "所有现有测试继续通过，无测试期望值被修改" |

## 核心原则

1. **聚焦 WHAT，而非 HOW**：
   - 好的目标："实现接口 Processor，使其能通过所有测试"
   - 坏的目标："创建一个结构体，添加 Process 方法，返回字符串"

2. **成功 = 错误解决 + 最小变更**：
   - 修复成功 = "这个特定的编译错误被解决，且变更最小"
   - 如果修复引入了新错误，STOP 并重新考虑

3. **禁止优雅性优化**：
   - 不要为 "更优雅" 而重构
   - 优化目标是 "正确性 + 简单性"，不是 "完美"

4. **失败即停止**：
   - 如果修复引入了新错误，不要继续打补丁
   - 回到 Think Phase，重新分析根因

## 成功标准模板

每个任务必须定义以下成功标准：

- [ ] **构建通过**：`go build ./...` 返回零错误
- [ ] **测试通过**：`go test ./...` 通过（现有测试不被破坏）
- [ ] **简单性**：变更行数在预算内（生成 ≤200，修复 ≤50）
- [ ] **外科手术式**：只修改了声明范围内的文件
- [ ] **目标达成**：任务目标中描述的具体错误/需求被解决

## 检查清单

- [ ] 目标是用声明式语言描述的
- [ ] 成功标准可验证（是/否）
- [ ] 没有将 "步骤" 误认为 "标准"
- [ ] 如果修复引入新错误，已停止并重新分析
