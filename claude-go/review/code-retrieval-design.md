# 代码检索与代码智能设计

> **版本**: 1.1
> **日期**: 2026-05-16
> **范围**: 面向大型代码库（MySQL/Linux 级别）的 LLM Agent 代码理解
> **目标**: 在保证精度的前提下最小化 Token 消耗；支持分支切换与持续开发更新

---

## 1. 问题分析

### 1.1 现状

现有 Agent 完全依赖内置工具（`Read`、`Grep`、`Glob`、`Bash`）进行代码库导航。对于大型代码库，这种方式存在三个致命缺陷：

1. **Token 消耗过高**: `grep` + `Read` 的组合往往会把成千上万行无关代码拉进上下文。单次 `grep -r` 在大型代码库上可能返回 5 万+ Token 的噪音。
2. **缺乏结构感知**: 模型无法直接看到"谁调用了这个函数"或"哪些文件依赖这个模块"，必须串行执行多次工具调用，每次都在燃烧 Token。
3. **无分支感知**: 工具只能操作当前工作目录的文件。切换分支后需要重新读取所有内容；没有按分支缓存的结构索引。

### 1.2 Token 成本对比

| 场景 | 原始 Grep+Read 方案 | 混合检索方案 | 节省 |
|------|---------------------|-------------|------|
| 查找 `tcp_congestion_control` 定义 | 搜索 12 个文件 × 500 行 = 6000 行 | 图查询 + 1 个定义 + 3 个调用方 = 200 行 | **30 倍** |
| "修改这个结构体会影响什么？" | 手动在仓库中 grep 结构体名 | 代码属性图上的影响半径查询 | **50 倍** |
| 理解一个模块的用途 | 顺序读取 5-8 个文件 | 知识图谱中的社区摘要 | **20 倍** |
| 自然语言查询 | 无此能力 | 向量嵌入检索 | **新增能力** |

## 2. 设计原则

1. **精度优先**: 对于结构查询，确定性结果（AST/图/LSP）优于概率性结果（向量/LLM）。
2. **Token 预算感知**: 每次检索操作必须声明预估 Token 成本；Agent 编排器可以拒绝昂贵的查询。
3. **增量更新**: 只重新索引变更的文件，而非整个仓库。
4. **分支隔离**: 每个分支维护自己的结构覆盖层；切换分支是 O(1) 的指针交换。
5. **优雅降级**: 如果智能索引过期或缺失，自动回退到现有的 `grep`/`Read` 工具。

## 3. 四层混合架构

```
┌─────────────────────────────────────────────────────────────────────┐
│  第四层: 编排器与查询路由                                             │
│   - 意图分类（定义查询 / 语义查询 / 影响分析 / 审计）                   │
│   - 执行前预算检查                                                   │
│   - 结果去重（RRF 排序）                                             │
│   - 上下文剪枝: 只向 LLM 发送最小相关子图                              │
└─────────────────────────────────────────────────────────────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
   ┌─────────┐            ┌──────────┐           ┌──────────┐
   │ 第一层  │            │ 第二层   │           │ 第三层   │
   │ 快速    │            │ 结构图   │           │ 精确导航 │
   │ 文本搜索│            │ (AST)   │           │ (SCIP)  │
   └─────────┘            └──────────┘           └──────────┘
        │                       │                       │
   Zoekt / ripgrep         Tree-sitter + 图数据库      LSIF/SCIP
   < 10ms                  < 100ms                    < 500ms
   精确匹配                 调用/导入图                 交叉引用
   无结构                   社区检测                    类型解析
```

### 3.1 第一层: 快速文本搜索（Zoekt / ripgrep）

**用途**: 精确字符串匹配、正则搜索、审计查询。

**技术选型评估**:

| 方案 | 成熟度 | 索引速度 | 查询延迟 | 维护成本 | 推荐度 |
|------|--------|---------|---------|---------|--------|
| **Zoekt** | 高（Google 开源，Sourcegraph 使用） | 中等 | < 10ms（亿级代码行） | 低（Go 实现，单二进制） | **首选** |
| **ripgrep** | 极高 | 无索引（实时搜索） | 10-500ms（视仓库大小） | 极低 | **冷启动/备用** |
| **OpenGrok** | 中等 | 慢 | 中等 | 高（需 Java + Tomcat） | 不推荐 |
| **LiveGrep** | 高 | 快 | < 10ms | 中等 | 备选 |

**推荐策略**:
- **主力**: Zoekt。Google 内部使用多年，Sourcegraph 的核心搜索引擎，基于三元组索引，亚秒级查询数十亿行代码。
- **备用**: ripgrep。用于未索引文件、特性分支或离线场景。

**何时使用**:
- 查找特定字符串的所有出现位置（错误信息、TODO、函数名）
- 基于正则的模式匹配
- 图索引构建完成前的冷启动阶段

**Token 策略**: 只返回文件路径 + 行号 + 1 行上下文。从不返回完整文件内容。

---

### 3.2 第二层: 结构图（Tree-sitter + 图数据库）

**用途**: Token 高效的结构性理解。大多数 Agent 查询的主要检索层。

**技术选型评估——解析器**:

| 方案 | 语言支持 | 增量解析 | 性能 | 推荐度 |
|------|---------|---------|------|--------|
| **Tree-sitter** | 30+ 语言 | 支持（毫秒级） | 单文件 < 1ms | **首选** |
| **ANTLR** | 广泛 | 不支持 | 中等 | 不推荐（无增量） |
| **libclang** | C/C++/ObjC | 不支持 | 快 | 仅 C++ 精确场景备用 |
| **Go AST** | 仅 Go | 不支持 | 极快 | Go 专用场景 |

**技术选型评估——图数据库**:

| 方案 | 查询语言 | 嵌入式 | 性能 | 维护成本 | 推荐度 |
|------|---------|--------|------|---------|--------|
| **KuzuDB** | Cypher | 是（C++ 嵌入式） | < 100ms（2 跳查询） | 低 | **首选** |
| **SQLite + 递归 CTE** | SQL | 是 | < 200ms | 极低 | **备选/过渡** |
| **Neo4j** | Cypher | 否（需独立服务） | 快 | 高 | 不推荐（运维重） |
| **DuckDB + 图扩展** | SQL | 是 | 中等 | 低 | 观望 |

**推荐策略**:
- **解析器**: Tree-sitter。唯一支持增量解析的开源方案，已集成到 GitHub、Atom、NeoVim。
- **图数据库**: KuzuDB 为主，SQLite 为过渡。KuzuDB 是原生嵌入式图数据库（Cypher 查询），无需独立服务；若团队不熟悉 Cypher，可先用 SQLite + 递归 CTE 验证概念。

**图结构**:
```cypher
(:文件 {路径, 哈希, 语言, 分支})
(:符号 {名称, 类型, 行号, 签名, 哈希})
(:模块 {名称, 社区编号})

(:文件)-[:包含]->(:符号)
(:符号)-[:调用]->(:符号)
(:符号)-[:导入]->(:符号)
(:符号)-[:继承]->(:符号)
(:符号)-[:定义于]->(:文件)
(:模块)-[:包含]->(:文件)
```

**查询示例**:
```cypher
// 查找函数定义 + 调用方（2 跳）
MATCH (f:符号 {名称: "initConnectionPool"})-[:定义于]->(文件)
OPTIONAL MATCH (调用方:符号)-[:调用]->(f)
RETURN 文件.路径, f.行号, collect(调用方.名称)[0..5]

// 影响半径: 哪些文件依赖这个文件？
MATCH (f:文件 {路径: "src/db/pool.go"})-[:包含]->(s:符号)
OPTIONAL MATCH (s)<-[:调用|导入]-(依赖:符号)-[:定义于]->(依赖文件:文件)
RETURN 依赖文件.路径, count(*) AS 依赖数 ORDER BY 依赖数 DESC
```

**Token 策略**: 只返回子图（目标符号 + 调用方 + 被调用方，限制在 2 跳内）。通常 200-800 Token，对比原始文件读取的 5000+ Token。

### 3.3 第三层: 精确导航（SCIP / LSP）

**用途**: 准确的交叉引用、类型解析、方法重写链。

**技术选型评估**:

| 方案 | 确定性 | 延迟 | 构建成本 | 语言覆盖 | 推荐度 |
|------|--------|------|---------|---------|--------|
| **SCIP** | 高（预计算） | < 500ms | 需 CI 构建 | 多语言 | **首选（CI 场景）** |
| **LSP** | 高（实时） | 50-2000ms | 需语言服务器 | 取决于 LSP 实现 | **实时场景** |
| **LSIF** | 高 | < 500ms | 需 CI 构建 | 多语言 | **已弃用（被 SCIP 替代）** |
| **ctags** | 中 | < 100ms | 极低 | 广泛 | **冷启动备用** |
| **Guru** | 高 | 慢 | 中等 | 仅 Go | Go 专用 |

**推荐策略**:
- **主力**: SCIP。Sourcegraph 推出的 LSIF 继任者，语言无关、确定性强、可审计。在 CI 中为主分支预构建索引。
- **实时补充**: LSP 语言服务器。当 SCIP 索引过期或需要当前未保存文件的导航时，通过 LSP 协议查询。
- **备用**: ctags。无需构建，秒级生成，精度虽不如 SCIP 但远胜于文本搜索。

**何时使用**:
- "查找所有引用"（AST 单独不够的场景：泛型、方法重写、动态分发）
- 类型层级查询（"哪些类型实现了这个接口？"）
- 复杂语言中的跳转到定义（C++、Rust、Java）

**Token 策略**: SCIP 返回符号位置（文件 + 行号 + 列号），不返回内容。内容通过 `Read` 按 offset/limit 按需获取。

---

### 3.4 第四层: 向量嵌入（可选增强）

**用途**: 自然语言到代码的映射（"认证逻辑在哪里处理？"）。

**技术选型评估**:

| 组件 | 方案 | 特点 | 推荐度 |
|------|------|------|--------|
| **嵌入模型** | CodeBERT / GraphCodeBERT | 预训练代码嵌入，7K+ stars | **首选** |
| **嵌入模型** | Jina Embeddings / BGE | 通用但代码表现好 | 备选 |
| **向量数据库** | **Qdrant** | Rust 实现，嵌入式或独立，HNSW | **首选** |
| **向量数据库** | pgvector | PostgreSQL 扩展 | 已有 PG 时首选 |
| **向量数据库** | Weaviate | 云原生，功能丰富 | 云部署首选 |
| **向量数据库** | Milvus | 分布式，企业级 | 超大规模备选 |

**推荐策略**:
- **嵌入模型**: CodeBERT（轻量，适合本地）或 GraphCodeBERT（带结构信息，效果更好）。也可直接复用主 LLM 的嵌入能力（如果 API 支持）。
- **向量库**: Qdrant（单机性能最优，Go/Rust 生态友好）或 pgvector（如果团队已有 PostgreSQL 基础设施）。

**重要警告**: 这是**精度最低**的一层。结果在送给 LLM 前，必须经第二层或第三层交叉验证。

## 4. 与现有工具的集成

**不是替代，而是路由增强。**

现有工具（`Read`、`Grep`、`Glob`、`Bash`）仍然可用。代码智能层新增 **MCP 工具**供模型选择使用：

| 新工具 | 对应层级 | 替代/增强 |
|--------|---------|----------|
| `code_navigate` | 第二层/第三层 | 替代 `Grep` + `Read` 的结构性查询链 |
| `code_impact` | 第二层 | 替代手动 grep 的"修改 X 会破坏什么" |
| `code_semantic` | 第四层 | 新增能力（无替代） |
| `code_status` | 索引管理器 | 替代 `git status` + 手动文件检查 |

**降级规则**: 如果智能索引返回无结果或已过期，编排器自动回退到 `Grep` + `Read`。

### 4.1 示例: 替换 5 步工具链

**之前（当前）**:
1. `Grep` 函数名 → 15 个匹配
2. `Read` 文件 A 理解调用点 → 300 行
3. `Read` 文件 B 理解被调用方 → 400 行
4. `Grep` 文件 A 的导入 → 8 个匹配
5. `Read` 文件 C 理解接口 → 250 行
**总计**: ~950 行，~3000 Token

**之后（使用 code_navigate）**:
1. `code_navigate` 查询 `{"symbol": "initConnectionPool", "depth": 2}`
**结果**:
```json
{
  "definition": {"file": "src/db/pool.go", "line": 45},
  "callers": [
    {"file": "src/api/server.go", "line": 120, "symbol": "startServer"},
    {"file": "src/worker/job.go", "line": 88, "symbol": "runJob"}
  ],
  "callees": [
    {"file": "src/db/pool.go", "line": 60, "symbol": "createPool"}
  ]
}
```
2. 按需从 3 个文件中读取特定行
**总计**: ~60 行，~200 Token

## 5. 增量更新策略

### 5.1 触发重新索引的条件

| 变更类型 | 操作 | 延迟 |
|---------|------|------|
| 单个文件编辑 | 仅重新解析该文件的 AST | ~50-200ms |
| 文件重命名/移动 | 更新路径元数据 | ~10ms |
| 新增文件 | 解析并插入 | ~50-200ms |
| 删除文件 | 删除节点 + 相关边 | ~10ms |
| Git 切换分支 | 交换图指针 | ~O(1) |
| 跨文件影响 | 下次查询时惰性重算 | ~0ms（延迟） |

### 5.2 内容寻址缓存

```go
// file_hash_cache.go
func shouldReindex(path string) bool {
    oldHash := cache.Get(path)
    newHash := xxh3.Sum64(readFile(path))
    if oldHash == newHash {
        return false  // 跳过重新解析
    }
    cache.Set(path, newHash)
    return true
}
```

- XXH3 哈希: ~2GB/s 吞吐量，开销可忽略
- 存储: 每文件 8 字节（仅哈希，不含内容）
- 10 万文件: ~800KB 内存

### 5.3 影子图用于原子更新

```
主图 ──► 影子图（可写）
              │
              │ 索引完成后提交
              ▼
           主图（原子交换）
```

查询不会被索引阻塞。影子图增量构建完成后原子交换。

### 5.4 增量调用图算法（Zhao et al., ICSE 2023）

对于调用图更新（最昂贵的操作）：
1. 从 git diff 中收集变更的方法。
2. 从旧调用图中剪除失效的节点/边。
3. 收集受影响的方法（新可达的、超类方法、直接调用方）。
4. 只分析受影响方法的新版本。
5. 清理不可达节点。

**结果**: 比全量重建快 20 倍，内存减少 58%，存储减少 10%。

## 6. 分支处理

### 6.1 推荐策略: 分支隔离图 + 写时复制

```
graph/
  main/
    nodes.db
    edges.db
  feature/auth-refactor/
    delta.json  // 写时复制覆盖层
    nodes.db    // 仅变更的节点
```

**读取路径**:
1. 加载 `graph/main/` 作为基础
2. 应用 `graph/<分支>/delta.json` 覆盖层
3. 查询合并后的视图

**写入路径（文件编辑时）**:
1. 计算文件哈希；如果变更，将新节点写入分支覆盖层
2. 重新计算局部边（变更文件内的调用方/被调用方）
3. 更新 delta.json

**存储优化**: AST 节点的内容寻址存储。跨分支的相同 AST 自动去重。

### 6.2 处理变基和强制推送

```go
func handleBranchSwitch(newBranch string, newCommit string) {
    oldCommit := getIndexedCommit(newBranch)
    if isAncestor(oldCommit, newCommit) {
        // 快进: 应用增量 diff
        applyGitDiff(oldCommit, newCommit)
    } else {
        // 非快进（变基/强制推送）
        // 方案 A: 从最近共同祖先重新应用补丁
        base := mergeBase(oldCommit, newCommit)
        invalidateFrom(base)
        applyGitDiff(base, newCommit)
        // 方案 B: 全量重新索引（备用，罕见情况）
    }
}
```

## 7. Token 效率分析

### 7.1 各层检索成本

| 层级 | 查询类型 | 平均结果大小 | Token 数 |
|------|---------|-------------|---------|
| 第一层 (Zoekt) | `grep "TODO"` | 20 个文件路径 | 200 |
| 第二层 (图) | `查找 X 的调用方` | 3 个符号 + 位置 | 150 |
| 第二层 (图) | `file.go 的影响半径` | 8 个文件 + 依赖计数 | 300 |
| 第三层 (SCIP) | `查找所有引用` | 12 个位置 | 250 |
| 第四层 (向量) | `语义搜索` | 5 个代码块（每块 100 行） | 800 |
| **原始 (Read)** | `读取完整文件` | 3 个文件 × 300 行 | **3600** |

### 7.2 上下文剪枝规则

向 LLM 发送检索结果前，应用以下剪枝规则：

1. **去重**: 如果文件在多个查询结果中出现，合并后只发送一次。
2. **行数限制**: 每个文件最多发送相关符号周围 80 行上下文。
3. **深度限制**: 调用图截断在 2 跳（调用方的调用方）。
4. **社区过滤**: 如果目标符号属于检测到的社区（模块），只包含该社区内的文件以及直接外部依赖。

## 8. 开源组件 + 自研的混合实施方案

### 8.1 核心原则: 不重复造轮子，但保留控制权

| 层级 | 自研部分 | 开源组件 | 理由 |
|------|---------|---------|------|
| **第一层** | 查询路由、结果格式化 | **Zoekt**（索引与搜索） | Google 验证的搜索引擎，Go 实现，与代码库同生态 |
| **第一层备用** | 集成层 | **ripgrep** | 无需索引，零维护成本 |
| **第二层解析** | AST 到图模型的映射、增量更新调度 | **Tree-sitter**（解析器） | 唯一支持增量解析的工业级方案 |
| **第二层存储** | 图 schema 定义、查询生成器 | **KuzuDB**（图数据库） | 嵌入式 Cypher，无需运维独立服务 |
| **第三层** | 索引生命周期管理、回退逻辑 | **SCIP**（索引格式）+ **lsif-go/lsif-java** 等 | Sourcegraph 标准，多语言支持 |
| **第三层实时** | LSP 客户端封装、超时处理 | **gopls**、**clangd** 等语言服务器 | 各语言社区维护 |
| **第四层** | 嵌入流水线、检索后验证 | **Qdrant** 或 **pgvector** + **CodeBERT** | 专注向量检索，不自研索引算法 |
| **编排层** | 意图分类、预算检查、RRF 排序、降级逻辑 | — | 业务核心，必须自研 |

### 8.2 为什么不纯自研

| 组件 | 纯自研成本 | 开源替代收益 |
|------|-----------|-------------|
| 搜索引擎 | 6-12 人月（三元组索引、倒排、排名） | Zoekt 直接可用，Sourcegraph 已验证 |
| 解析器 | 3-6 人月/语言（且无增量支持） | Tree-sitter 30+ 语言，增量解析 |
| 图数据库 | 6-9 人月（存储引擎 + 查询优化） | KuzuDB 原生 Cypher，嵌入式 |
| 向量检索 | 3-6 人月（HNSW、量化、分布式） | Qdrant/pgvector 已解决 |
| LSP/SCIP | 语言语义分析是领域专家工作 | 各语言社区的语言服务器 |

**纯自研的总投入**: 约 20-40 人月，且需要持续跟进语言新特性（Go 泛型、Rust edition 等）。
**混合方案的总投入**: 约 4-8 人月（集成 + 编排层 + 图 schema），其余精力聚焦在业务逻辑上。

### 8.3 自研必须保留的核心能力

1. **编排层（查询路由器）**: 这是竞争壁垒。意图分类、Token 预算、多层结果融合、降级策略，与业务场景深度耦合，无法外包。
2. **增量更新调度器**: 开源组件提供原子能力（Tree-sitter 解析、KuzuDB 查询），但"何时触发、如何合并分支覆盖层、如何与 git hook 联动"是自有工作流。
3. **图 Schema 与查询生成**: AST 节点如何映射到图的节点/边，查询模板如何根据 LLM 意图生成 Cypher，这是领域模型。
4. **结果到 LLM 的上下文剪枝**: 200 行的子图如何剪成 60 行最有信息量的内容，需要自研启发式规则。

## 10. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 索引在活跃开发时过期 | 中 | Git hooks 自动触发重索引；查询路由器检查新鲜度并向 LLM 发出警告 |
| Tree-sitter 解析器在畸形代码上崩溃 | 低 | 解析器沙箱运行在独立进程中；回退到文本搜索 |
| 分支隔离导致存储爆炸 | 中 | 内容寻址去重；30 天后清理旧分支图 |
| 查询延迟不可接受 | 低 | 第一层（Zoekt）< 10ms；第二层 < 100ms；慢查询可取消 |
| LLM 忽略新工具 | 中 | 在系统提示词中包含工具使用示例；与旧工具链做 A/B 对比测试 |
| 开源组件版本不兼容 | 低 | KuzuDB、Zoekt、Qdrant 均提供稳定 API；锁定版本并通过 CI 验证 |
| SCIP 索引构建失败 | 中 | CI 中构建 SCIP 作为非阻塞步骤；失败时自动降级到 LSP/Tree-sitter |
