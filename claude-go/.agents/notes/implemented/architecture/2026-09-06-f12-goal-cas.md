# Agent Note: F12 目标状态机 CAS — 事件溯源 + 乐观并发

Status: implemented

[English](2026-09-06-f12-goal-cas.en.md) | 中文

## Problem

动态工作流的目标分解 (design/01 §4.5) 已有目标树, 但多 agent 同时改目标**无冲突检测**: 内部迁移是"最后写者胜", 任何外部更新者都能用无版本检查的读改写**静默覆盖**别人的变更。规格 (docforge planning-dsh-adopt F12, dsh `packages/goal/store`) 要求: 目标状态机以事件溯源存储, 更新带乐观并发控制, 冲突即拒绝。

本仓的现实落点不是 GoalTree (已删, 见 orch-dynamic), 而是 **TaskService 的任务档案状态机**。

## Decision

**档案 KV 是投影, journal 是唯一真源; 内部迁移保持最后写者胜, 外部更新必须 CAS。**

1. **事件溯源**: `tasks-journal` 事件流 (`TaskJournalEvent`: Seq/TS/Task/From/To/Revision/Note/Conflict) 是唯一真源; 档案 KV 是它的投影。Seq 单调、Revision 是事件后档案修订号——链条连续即可重放出状态机演进史 (`ReadJournal`)。**CAS 冲突被拒也要留痕** (`Conflict: true`)——被拒绝的更新正是审计价值所在。
2. **`TransitionCAS(id, expectRevision, mutate)`**: 携带读到的 Revision 做期望检查, 不匹配返回 `ErrStateConflict`。`mutate` 拿到未加锁的档案副本, 在其上声明目标状态与字段变更; 修订号由服务维护, mutate 不必也不能自增。返回 `(nil, nil)` 表示本次不落盘。
3. **双轨并发纪律** (有意保留两种模式): 内部迁移 (`transition`) 保持最后写者胜——它们是状态机自身的推进 (running/failed/…), 改成 CAS 只会平添无意义的冲突; 外部多 agent 更新**必须**走 `TransitionCAS` / `Refine`, 不再允许无版本检查的读改写。
4. **不承诺跨进程幂等**: statestore FileStore 锁是 per-instance 的, 两个进程指向同一 stateDir 并发 Submit 仍可能各建一份档案。CAS 解决的是**同实例内**多 agent 并发; 跨进程幂等由动作队列的 os.Rename 认领承担。边界在 taskservice.go 包注释里明文记录。
